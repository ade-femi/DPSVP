# Synthea → FHIR → OMOP: A Governed Reference Pipeline

An end-to-end, reproducible pipeline that generates synthetic patient
populations, exports them as FHIR R4 Bundles, transforms them into the OMOP
Common Data Model (CDM) v5.4, and wraps that transformation in a governance
layer: validation, logging, and an auditable data-quality report on every run.

Every record here is synthetic, generated by
[Synthea](https://github.com/synthetichealth/synthea) (Apache 2.0, MITRE
Corporation). There is no PHI, no IRB, and no data use agreement — the whole
thing runs from zero on open-source tools.

## Project status: active development

**This is a working pipeline under active development, not a finished product.**
The path from Synthea to a populated, validated OMOP CDM runs end to end today
and is exercised in CI on every push — but the scope is deliberately narrow,
several pieces are known-incomplete, and the design is still moving.

What works today:

- Synthea → FHIR R4 → OMOP CDM v5.4 in Postgres, six tables, verified against a
  real database ([example report](reports/example/))
- Governance layer: four check families, per-row exclusion accounting, a dated
  report per run
- 25 tests, CI on Python 3.10 and 3.12 plus an end-to-end run against Postgres

Known-incomplete, in rough priority order:

- [ ] **Vocabulary mappings are unverified.** The ~14 bundled `concept_id`
      values have not been checked against Athena — see
      [Known limitations](#known-limitations). This is the next task.
- [ ] Load the full OHDSI Athena vocabulary to replace the hand-curated map
- [ ] Validate the populated CDM against OHDSI's Data Quality Dashboard for an
      external quality score
- [ ] Incremental / upsert loads (currently full-refresh only)
- [ ] Additional domains: Procedure, Immunization, DeviceExposure
- [ ] Define a cohort in OHDSI ATLAS against the loaded CDM, to demonstrate the
      full data → cohort → analysis chain

Expect interfaces, table coverage, and the concept map to change. The
[commit history](../../commits/main) is the running record of what changed and
why.

## Why this exists

Health systems, payers, and researchers standardize on two things: **FHIR**
(HL7's standard for how clinical systems exchange data) and **OMOP CDM**
(OHDSI's standard for how that data is structured for observational research).
Almost no real-world data arrives already in OMOP, so someone has to build and
govern the ETL that gets it there. That transformation is what this repo
demonstrates:

1. **Ingestion** — realistic, standards-compliant clinical data (Synthea/FHIR)
2. **Transformation** — FHIR resources mapped to OMOP CDM tables, including the
   harder part: terminology mapping (SNOMED, LOINC, RxNorm → OMOP standard
   concepts)
3. **Governance** — every run validates what it produced, logs what it did with
   each row, and writes a report you can read afterwards

The governance layer is the point rather than a wrapper around it. Validating
at each transformation step, logging what happened to every row, and leaving an
auditable record generalizes across domains — the discipline is the same
whether the pipeline moves planning-application data or clinical data. Building
it against open standards instead of one employer's internal schema is what
makes the result portable.

It connects to a separate line of published research applying stacked
heterogeneous learning to depression-severity prediction, and deep learning to
disease-progression prediction in diabetic patients, on U.S. federal
population-health data (NHANES):

> Ayodele, A., Adetunla, A., Akinlabi, E. (2025). Depression Severity
> Prediction Using Stacked Heterogenous Learning on Integrated Biomedical
> and Lifestyle Data. *International Journal of Online and Biomedical
> Engineering (iJOE)*, 21(14), pp. 156–167.
> https://doi.org/10.3991/ijoe.v21i14.56383

OMOP is the shared substrate between the two: a cohort defined on this
synthetic data and a cohort defined on NHANES-derived data can both run through
the same OHDSI tooling (ATLAS, cohort characterization). This repo is the
data-infrastructure side of that problem. Depression and cardiometabolic
disease are bidirectionally linked and easily missed when the data feeding a
predictive model is fragmented, ungoverned, or arrives too late to act on.

**Scope.** This is an in-progress, synthetic-data reference implementation of a
pipeline methodology. It is not production healthcare infrastructure, has not
been validated against real patient data, and is not deployed anywhere.
Synthetic data with no PHI is precisely what makes it publishable in full, and
equally what bounds what it can claim.

## Architecture

```
Synthea (Java)                 FHIR R4 Bundles              OMOP CDM v5.4 (Postgres)
┌─────────────────┐   JSON    ┌──────────────────┐   ETL   ┌────────────────────┐
│ Synthetic patient│──────────▶│ Patient, Condition│────────▶│ person             │
│ generator        │  bundles  │ Observation,       │ Python │ visit_occurrence   │
│ (population.     │           │ MedicationRequest,│  (this │ condition_occurrence│
│  properties)     │           │ Encounter...       │  repo) │ drug_exposure      │
└─────────────────┘           └──────────────────┘         │ observation/measure │
                                                              └──────────┬─────────┘
                                                                         │
                                                              ┌──────────▼─────────┐
                                                              │ Governance layer    │
                                                              │ - schema validation │
                                                              │ - referential checks│
                                                              │ - concept coverage  │
                                                              │ - run-level report  │
```

See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for the full data flow,
including why validation runs before rows are excluded rather than after, and
[docs/MAPPING_DECISIONS.md](docs/MAPPING_DECISIONS.md) for which FHIR fields
map to which OMOP fields and on what reasoning.

## A real run

A report from a full run is checked in at
[reports/example/](reports/example/) — unedited, including the checks it
flags. It's a snapshot of the current state rather than a finished benchmark;
the numbers will move as the concept map and table coverage grow. That run,
against a Synthea population and a Postgres 16 instance carrying the official
OHDSI v5.4 DDL:

| | |
|---|---|
| Patient bundles read | 365 (from 367 files; 2 are Synthea's non-patient metadata bundles) |
| Rows loaded | 365 `person`, 21,819 `visit_occurrence`, 13,730 `condition_occurrence`, 19,321 `drug_exposure`, 158,803 `measurement`, 46,536 `observation` |
| Validation checks | 17 run, 13 passed, 4 flagged |
| Rows excluded from load | 0 |

The 4 flagged checks are all `concept_coverage`, and are the expected result of
shipping a small hand-curated concept map instead of the full Athena
vocabulary — see [Known limitations](#known-limitations). A run reporting full
coverage would mean the map had been padded.

Two properties of that report are worth knowing, because they are what the
governance claim rests on:

- **`fk:person_id` reporting zero failures is a real result.** Validation runs
  against the full mapped tables *before* any row is excluded. Feed the
  pipeline a bundle with its `Patient` resource stripped out and those checks
  flag with genuine counts.
- **Rows can only leave the pipeline through one place**, which logs and counts
  them by reason (unresolvable subject reference, or a NULL in a column OMOP
  declares NOT NULL). The report's exclusions section is explicitly empty for
  this input rather than absent.

## Quickstart

Prerequisites: Docker, Java 17+, Python 3.10+. See
[setup/00_prerequisites.md](setup/00_prerequisites.md) for install steps on
Mac/Windows/Linux.

```bash
# 1. Stand up OMOP CDM v5.4 in Postgres (official OHDSI DDL)
cp .env.example .env
docker compose up -d
bash setup/03_get_omop_ddl.sh
bash setup/04_init_db.sh

# 2. Build Synthea and generate synthetic patients as FHIR R4 bundles
bash setup/01_get_synthea.sh
bash setup/02_generate_patients.sh 300

# 3. Run the ETL: FHIR bundles -> OMOP CDM, with governance checks
pip install -r requirements.txt
python etl/run_pipeline.py --input data/synthea_output/fhir --report-out reports/

# 4. Read the data-quality report
open reports/quality_report_<run-id>.md
```

Useful flags:

- `--truncate` empties the target tables first. **The load is append-only, so
  re-running without it against the same input duplicates every row.**
  Surrogate keys are deterministic, so `--truncate` makes a re-run an
  idempotent refresh.
- `--no-load` runs mapping, validation, and the report without touching
  Postgres — useful when iterating on mapping logic.

Run the tests with `pytest tests/`. They cover the mapping logic against
hand-built FHIR fixtures, and need no database.


## Known limitations

Stated explicitly, because a governance claim that hides its own gaps isn't one.
Some of these are deliberate scope decisions; others are simply not done yet and
are tracked in [Project status](#project-status-active-development) above.

- **The bundled concept map is unverified.** Its `concept_id` values were
  entered by hand and have *not* been checked against
  [athena.ohdsi.org](https://athena.ohdsi.org), so a row counted as mapped may
  still carry the wrong standard concept. Coverage percentages measure whether
  a row found *a* mapping, not a correct one. This is surfaced in every quality
  report and exposed as `concept_mapper.VERIFIED_AGAINST_ATHENA`. One wrong
  entry has already been caught this way — two conditions sharing a
  `concept_id` — and was removed rather than replaced with another guess.
- **Vocabulary mapping is partial.** Full FHIR-code → OMOP standard-concept
  mapping needs the OHDSI Athena vocabulary tables, which require a free
  Athena account and, for some vocabularies such as full RxNorm, a UMLS
  license. This repo ships the mapping logic plus a small bundled subset (see
  `etl/concept_mapper.py`); at scale you load the real
  `CONCEPT`/`CONCEPT_RELATIONSHIP` tables. Unmapped codes become
  `concept_id = 0` and are flagged, never dropped.
- **Database-level FK constraints against `CONCEPT` are deliberately not
  applied.** `setup/04_init_db.sh` loads tables, primary keys, and indices but
  skips `OMOPCDM_postgresql_5.4_constraints.sql`, because nearly every
  constraint in it targets vocabulary tables this repo doesn't populate —
  leaving them active makes every insert fail, including correctly mapped
  concept_ids. Referential integrity is enforced and reported at the
  application layer by `governance/validators.py` instead. Load the real Athena
  vocabulary and that constraints file can be applied as-is.
- **Domain coverage is narrow by choice** (Condition, Observation,
  MedicationRequest, Encounter → OMOP). Extending to Procedure, Immunization,
  and others follows the same pattern in `etl/`.
- **Loads are not incremental.** Each run assumes a fresh or truncated target;
  there is no upsert or change-data-capture. `--truncate` plus deterministic
  surrogate keys covers full-refresh idempotency, which is not the same thing.
- **Not validated against OHDSI's Data Quality Dashboard.** Running the
  populated CDM through OHDSI's own DQD package would give a
  standards-recognized quality score rather than only this repo's validators.
  Noted as future work in docs/ARCHITECTURE.md.
