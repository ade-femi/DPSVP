# Synthea → FHIR → OMOP: A Governed Reference Pipeline

**What this is:** an end-to-end, reproducible pipeline that generates synthetic
patient populations, exports them as FHIR R4 Bundles, and transforms them into
the OMOP Common Data Model (CDM) v5.4 — with a governance layer (validation,
logging, data-quality reporting) wrapped around the transformation step.

**What this is not:** a demo that touches real patient data. Every record in
this repository is generated by [Synthea](https://github.com/synthetichealth/synthea)
(Apache 2.0, MITRE Corporation), a synthetic patient simulator. No PHI, no IRB,
no data use agreement — the entire pipeline is runnable by anyone, from zero,
using only open-source tools.

## Why this exists

Health systems, payers, and researchers overwhelmingly standardize on two
things: **FHIR** (HL7's interoperability standard for how clinical systems
exchange data) and **OMOP CDM** (OHDSI's standard for how that data is
structured for large-scale observational research). Almost no real-world data
arrives already in OMOP — someone has to build and govern the ETL that gets it
there. That transformation is the actual skill this repo demonstrates:

1. **Ingestion** — realistic, standards-compliant clinical data (Synthea/FHIR)
2. **Transformation** — FHIR resources mapped to OMOP CDM tables, including
   the harder part: terminology/vocabulary mapping (SNOMED, LOINC, RxNorm →
   OMOP standard concepts)
3. **Governance** — the transformation is validated, logged, and produces an
   auditable data-quality report on every run, not just a one-off script

## Quickstart

Prerequisites: Docker Desktop, Java 17+. If you don't have these, start with
[setup/00_prerequisites.md](setup/00_prerequisites.md) — it has install steps
for Mac/Windows/Linux.

```bash
# 1. Stand up OMOP CDM v5.4 in Postgres (official OHDSI DDL)
docker compose up -d
bash setup/03_get_omop_ddl.sh
bash setup/04_init_db.sh

# 2. Get and build Synthea, generate synthetic patients as FHIR R4 bundles
bash setup/01_get_synthea.sh
bash setup/02_generate_patients.sh 300   # generates 300 synthetic patients

# 3. Run the ETL: FHIR bundles -> OMOP CDM, with governance checks
pip install -r requirements.txt
python etl/run_pipeline.py --input data/synthea_output/fhir --report-out reports/

# 4. Read the data-quality report
open reports/quality_report_<timestamp>.md
```

## Repository structure

```
setup/          Shell scripts + docs to install deps, run Synthea, load OMOP DDL
etl/            Python: FHIR parsing + per-domain OMOP mapping + orchestrator
governance/     Validation rules, logging config, quality report generator
sql/            (gitignored) downloaded OHDSI CommonDataModel DDL lands here
docs/           Architecture, mapping decision log, governance rationale
tests/          Unit tests on the mapping logic using small fixture bundles
data/           (gitignored) Synthea output and any intermediate files
reports/        (gitignored) generated data-quality reports, one per run
```

## Known limitations (stated explicitly — this is part of the governance claim)

- **Vocabulary mapping is partial.** Full FHIR-code → OMOP standard-concept
  mapping requires the OHDSI Athena vocabulary tables, which need a free
  Athena account and, for some vocabularies (e.g. full RxNorm), a UMLS
  license. This repo ships mapping logic and a small bundled subset of common
  concepts (see `etl/concept_mapper.py`); at full scale you load the real
  Athena `CONCEPT`/`CONCEPT_RELATIONSHIP` tables. Unmapped codes are recorded
  as `concept_id = 0` and flagged in the quality report — never silently
  dropped.
- **Domain coverage is deliberately narrow** (Condition, Observation,
  MedicationRequest, Encounter → OMOP) rather than exhaustive, per the "modest
  and real" scope. Extending to Procedure, Immunization, etc. follows the
  same pattern in `etl/`.
- **Not validated against OHDSI's Data Quality Dashboard (DQD)** — that's a
  natural next step once the CDM is populated, and is noted as future work in
  docs/ARCHITECTURE.md.
